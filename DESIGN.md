## Overview

Writers Block is a monochrome, focused songwriting workspace. The interface should feel like a sheet of paper with a capable assistant close at hand: one flat writing surface, ink-coloured text and actions, large serif song titles, restrained controls, and hue only where it helps the writer read rhythm, rhyme, or status.

Naming: the product's user-facing name is "Writers Block" on both platforms (iOS `CFBundleDisplayName`, Android `app_name`, the welcome wordmark, and the README). "RhymeAI" is the repository and code namespace only (`RhymeAITokens`, `RhymeAITheme`, package `com.rhymeai.app`). It still appears in UI copy in two places on both platforms: as the brand of the app's own on-device models (the "RhymeAI Gemma" download titles and the "RhymeAI Gemma Downloads" section in Settings), in the import error "Pick a RhymeAI project JSON", which names the project file format, and on iOS in the local-model error "This GGUF model is not registered with RhymeAI". This list was built by searching the code and may not be complete. Do not use the name for the app in new copy.

Both platforms ship the same three appearances, chosen by the user in Settings under Appearance with a three-segment control:

- **Ink** (default, and the fallback for an unknown stored value): near-white canvas with near-black ink. Light colour scheme.
- **Paper**: warm ivory canvas with soft pencil-grey ink. Light colour scheme.
- **Graphite**: near-black canvas with warm white ink. Dark colour scheme, and the only appearance that uses the pastel analysis palette.

The appearance is an explicit user choice. It does not follow the system light/dark setting, and Android does not use Material You dynamic colour. Each appearance forces its own colour scheme (iOS `preferredColorScheme`; Android `lightColorScheme`/`darkColorScheme`).

Each platform keeps its native structure. Android is built from Material 3 components themed by `RhymeAITheme`. iOS is SwiftUI with opaque, bordered surfaces; despite the `liquidGlassSurface` name, iOS surfaces use no blur, material, or `glassEffect`. The shared identity is the monochrome palettes, the serif/sans pairing, and the lyric-first hierarchy.

Evidence: iOS statements were checked against the code and against current simulator screenshots (iPhone and iPad, all three appearances, default and accessibility text sizes). There are no current Android screenshots; Android statements come from code only.

## Typography

The typographic voice pairs a bold system serif for song identity with the plain system sans for everything else. No custom font files ship on either platform.

Serif (iOS `design: .serif`, Android `FontFamily.Serif`) is used on both platforms for the welcome wordmark, the editor's song title field, the Word Inspector headword, and — at regular weight — suggested lyric lines and the quoted target line in the assistant. Monospace is used on both platforms for IPA and syllable-count badges; iOS also uses it for the recording timer and API-key entry, where Android keeps the default sans. iOS uses the rounded design in two places: the suggestion tier badge and one settings field.

iOS uses Dynamic Type text styles rather than fixed sizes:

| Role | iOS style |
| --- | --- |
| Welcome wordmark, song title field, inspector headword | `largeTitle`, serif, bold |
| Lyrics | 16pt regular system font scaled with the `body` text style |
| Suggested line, quoted target line | `body`, serif |
| Primary button label, UnBlock wordmark | `body` semibold |
| Card and section titles, Save Settings | `headline` |
| Row titles, secondary buttons, toasts | `subheadline` (semibold or medium for emphasis) |
| Supporting text, word/syllable counts, chips, segmented labels | `caption` (semibold for emphasis) |
| Toolbar glyphs | 17pt medium system symbol in secondary ink; welcome and mic glyphs 20pt semibold |

Android uses the Material type scale in `Type.kt`: serif bold for `displayLarge` 44/52sp, `displayMedium` 40/48sp, `headlineLarge` 32/40sp, and `headlineMedium` 28/36sp (the welcome wordmark); sans for `titleLarge` 20/28sp medium, `titleMedium` 16/24sp medium, `bodyLarge` 16/24sp, `bodyMedium` 14/20sp, `bodySmall` 12/16sp, and `labelMedium` 12/16sp medium. The editor overrides two roles: the song title is serif bold 34/42sp, and lyrics are sans 17sp on a 27sp line. Secondary and support text uses the 13sp caption token (`DesignTokens.Typography.caption`); editor metadata is 13/16sp.

Dynamic Type behaviour on iOS is enforced in code, not left to chance:

- Lyrics, titles, and labels set with text styles scale with the user's text size. Symbol glyphs given a fixed point size (the 17pt toolbar icons, the 20pt welcome and mic icons, the 13pt chevron) do not scale.
- At accessibility sizes on a compact width, the editor top bar and the floating action row are clamped to the `large` size so the toolbar stays on one row; on a regular width the top bar instead splits into two rows.
- Multi-option rows restack vertically at accessibility sizes: welcome cards, custom segmented controls with more than two options, suggestion actions, and notebook actions. Rewrite chips instead switch to a horizontally scrolling row at natural width so the bar stays one line tall.
- The welcome screen drops the app icon and the subtitle at accessibility sizes so the three actions stay reachable.

Letter spacing stays neutral. Do not tighten display text; the heavy serif forms already carry enough character.

## Elevation & Depth

The interface is flat. Surfaces are separated by a 1px border and a small tonal step, not by blur; shadows are confined to the few places listed below.

On iOS most bordered surfaces go through `liquidGlassSurface`, which draws an opaque palette fill with a 1px border: resting surfaces use the surface colour and the outline colour; interactive surfaces use the raised surface colour and the strong outline. With Increase Contrast on, those borders all use the strong outline. A few controls draw their own 1px border instead and do not react to Increase Contrast: the custom segmented control, the Word Inspector chips, and the welcome app icon. There is no `.ultraThinMaterial`, `.glassEffect`, or blur in the iOS app, and `liquidGlassGroup` is a no-op.

Shadows on iOS are limited to five places:

- The welcome app icon: primary ink at 14%, radius 18, y 8.
- The UnBlock pill: primary ink at 26%, radius 12, y 4.
- The mic button and recording pill: primary ink at 18%, radius 12, y 4.
- The songs drawer panel: black at 35%, radius 26, x 10. The shadow is attached to the panel background only; it was deliberately removed from the drawer's content because it rendered as grey smudges under every control on the light appearances.
- Floating toasts in the drawer and recordings screen: black at 30%, radius 14, y 4.

Cards, rows, suggestion cards, chips, settings groups, the assistant panel, and the editor have no shadow.

On Android, depth is Material tonal colour plus 1dp borders. The drawer and settings page set tonal elevation to 0. The only elevations set explicitly in the UI code are the welcome app icon (4dp tonal, 6dp shadow) and the recordings selection bar (3dp tonal). The floating actions are flat fills. Stock Material components — alert dialogs, dropdown menus, modal bottom sheets, and snackbars — keep their default Material elevation.

Scrims are functional. The palette scrim is the ink colour at 42% on Ink and Paper and black at 55% on Graphite. The iOS songs drawer uses black at 42% in every appearance.

## Motion

Motion must explain cause, state, or spatial origin. iOS uses a three-tier golden-ratio duration ladder. Android shares the 160ms and 260ms tiers as constants; it has no 420ms constant and settles with a spring instead. The uses in the table are the iOS ones:

| Tier | Duration | Used for |
| --- | --- | --- |
| Feedback / dismiss | 160ms | Press states, save-status changes, drawer and sheet dismissal |
| State / presentation | 260ms | Segmented selection, welcome-to-editor fade, chips and toasts appearing, panels, sheets, and drawers presenting |
| Settle | 420ms | Drag release and disclosure settle |

iOS curves: feedback, dismiss, and state use ease-in-out; presentation is a spring (response 0.26, damping 0.88); settle is a spring (response 0.42, damping 0.80); the mic and UnBlock choreography uses the expressive spring (response 0.40, damping 0.76). Buttons that use the `rhymePress` style (most custom buttons) scale to 0.98 and fade to 86% opacity while pressed; the few buttons with system styles use the system press state.

Android curves: standard and emphasized easing are both cubic-bezier(0.2, 0, 0, 1); exit easing is cubic-bezier(0.4, 0, 1, 1). Springs mirror iOS: standard damping 0.88 (medium-low stiffness), settle damping 0.80 (low stiffness), expressive damping 0.76 with stiffness 247. Android also defines a 140ms page fade and a 200ms disclosure duration. The Android drawer presents in 260ms on the standard easing and dismisses in 160ms on the exit easing. Releasing the Android assistant sheet's handle dismisses it when the sheet, or the spline-decay projection of the release velocity, has passed half the sheet's travel (iOS checks the predicted end translation the same way); otherwise it settles back on the settle spring, starting from the finger's velocity.

Reduced motion is handled in code. On iOS, animations go through `rhymeAnimation` / `withRhymeAnimation` or an explicit Reduce Motion check, all of which disable the animation when Reduce Motion is on; the press style keeps its opacity change but drops the scale. Move and scale transitions also swap to opacity: the editor's floating actions, chip bar, and rewrite bar, the assistant sheet, the songs drawer's Trash screen and toasts, the Trash selection tick, and the cloud-backup disclosure. On Android, Compose honours the system animator duration scale, and custom drag and slide transitions snap when animations are disabled.

Suggestion loading is built from the same tiers. When a next-line request starts, the Suggestions section opens on the 260ms state tier with three ghost cards in the slots the lines will fill. Each streamed line takes the next slot in place, cross-fading out of its ghost on the state tier (Android settles any size change on the standard spring); lines past the third append below with the same fade, and any slot still empty when the stream ends or Stop is tapped leaves on the 160ms dismiss tier, the whole section with it when no line came. Each ghost is the suggestion card held to size by hidden text in the card's own fonts: the serif line, the stress-and-IPA rows when that preview is on, the syllable badge, and the two actions laid out the way the card lays them out (iOS `ViewThatFits`, Android the same `FlowRow` with the real buttons disabled and invisible). The ghost therefore grows with Dynamic Type and the Android font scale exactly as the card does, and a card landing in its slot only moves the list when its line or IPA runs past one line. While a ghost waits, its text bar is written like an ink line: it scales from the left over 420ms (the settle tier; iOS ease-in-out, Android standard easing), holds 260ms, fades over 160ms on the exit curve and rests 260ms, a 1,100ms loop with every step on the ladder, and the ghosts of one request write together. Resting bar: primary ink at 8%; stroke: 34%. A "Writing…" caption sits beside the Suggestions heading while the request runs; Android makes it a polite live region read as "Writing suggestions", and iOS posts that announcement when writing starts, the ghosts being hidden from assistive technology. The primary button's label (Suggest Next Line, Stop, and on Android Set up model) cross-fades in place on the state tier whenever it changes. Under Reduce Motion (iOS) the ghosts hold a still bar at 16% and the slot and label changes are not animated; on Android with animations removed the bar is still and every change snaps. iOS `SuggestionInkLineMotion`, Android `SuggestionPlaceholderMotion`.

Avoid decorative hover effects and staggered choreography unless they make state or motion origin clearer.

### Known inconsistencies

These describe the current code. They are not rules to copy.

- iOS recordings selection toolbar: the text-only Cancel, Delete and Select buttons in the songs drawer have no 44pt minimum frame, so their hit areas are the size of their text.
- Android word inspector result chips are below the touch-target minimum: 6dp vertical padding with no minimum size. The iOS chips have a 44pt hit area.
- Touch targets have not been audited control by control; other gaps may exist.
- Outside Settings, iOS still uses the system segmented picker: the drawer's Songs/Recordings switch, the notebook, the trash screen, and the assistant's rhyme-density control. Settings uses the custom control throughout.
- The iOS `Radius.xxl` (32pt) token is no longer used by any view.
- The editor's word and syllable totals reuse two syllable colours on both platforms (the 1-syllable colour for words, the 4+ colour for syllables) although they are totals, not per-word cues. The syllable legend does not mention them.
- The colour key for syllable counts and rhyme families is only in the help sheets behind the "?" buttons on the Editor tab of Settings ("Syllable Guide" and "Rhyme Families"); on Android the Analysis Style group on the General tab describes the styles in words without a key.
- Graphite switches have weak contrast on iOS: the on-state track is the warm white action colour (`#F6F2E8`) behind a white thumb.
- The songs drawer is full-width on iPad. The iOS layout tokens `drawerMinWidth`, `drawerMaxWidth`, `drawerHorizontalMargin`, `projectSidebarWidth`, and `threeColumnWorkspaceMinWidth` do not size the drawer (the first two only cap the welcome cards and chip bar; the last three are unused), and Android's `Drawer.compactWidth` and `Drawer.width` are unused.
- iOS still passes legacy hue tints (indigo, teal, cyan, purple, blue, white) into `liquidGlassSurface` for some settings groups and the rewrite review bar. They are applied at very low opacity and are not part of the palette. The `liquidGlass*` names are legacy too.
- iOS hardcodes black for the drawer scrim and for drawer and toast shadows instead of using the palette scrim.
- Token names disagree across platforms (for example `Spacing.lg` is 24pt on iOS and 20dp on Android; `Radius.pill` is 52pt and 28dp).
- Paper's ruled texture exists only on iOS, and Paper's selection colour differs (`#D8CDB4` iOS, `#D2C8B0` Android).
- Android maps both `outline` and `outlineVariant` to the strong outline, so resting borders are darker than on iOS, which uses the lighter outline at rest.
- Android has no save-failed state in the top bar and no persistent assistant side panel on large screens.
- Lyric size and bottom rest differ: 16pt and 200pt on iOS, 17sp and 300dp on Android.
- The iOS lyric editor's Ink and Paper rhyme colours come from a second array whose amber, green, orange, cyan, yellow, and lime entries differ from `AppAppearance` and from Android; the iOS assistant help sheet has a third copy.
- iOS uses system hues outside the palettes: system indigo on the two cloud-sharing consent switches (deliberate, for Graphite contrast); and system indigo, green, and orange for the suggestion tier badge. Android draws the tier badge from the colour scheme.
- The mic button is an action fill on iOS and an outlined high-container surface on Android. The recording timer is monospaced on iOS only.
- Welcome differs by platform: two sentences of copy and tiled icons on a raised surface on iOS; one line of copy, bare icons on `surfaceContainerLow`, and an extra "Continue" card on Android.
- Two iOS views use non-continuous rounded rectangles: `RhymeSchemeDisplayView` and the beat-grid preview.
- Android has no 420ms duration constant, and its dialogs, menus, bottom sheets, and snackbars keep stock Material elevation.
- Several iOS controls draw their own border (custom segmented control, inspector chips, app icon) and so ignore Increase Contrast.

## Do's and Don'ts

Do keep the lyric editor visually quiet: one flat canvas, ink text, no cards behind the lyrics.

Do take every colour from the active appearance's palette so a screen works in Ink, Paper, and Graphite without special cases.

Do use the action fill with its on-action colour for the one primary action on a surface.

Do use serif type for song identity and sans type for controls.

Do keep rhyme and syllable colours semantically stable.

Do separate surfaces with a 1px palette outline and a tonal step.

Do preserve platform-native behaviour: Material 3 components on Android, native sheets and Dynamic Type on iOS.

Do give every control a 44pt (iOS) or 48dp (Android) hit area and every icon button a label.

Do let actions and panels animate from their physical origin, and route animations through the reduced-motion helpers.

Don't add an accent hue, gradient, or tint to chrome. Hue is reserved for rhyme, syllable, and status meaning; the existing exceptions are listed under Known inconsistencies and should not be extended.

Don't reintroduce blur, translucent "glass" materials, or glow.

Don't add shadows to cards, rows, or panels; on iOS, shadows are limited to the floating actions, the app icon, the drawer edge, and toasts.

Don't follow the system light/dark setting or Android dynamic colour; appearance is the user's choice in Settings.

Don't hardcode black, white, or system greys where a palette role exists.

Don't make Android and iOS visually identical at the expense of platform conventions.

Don't use magic-wand imagery for UnBlock or context controls.

Don't let panel transitions snap, jump, or recenter after content has already appeared.
